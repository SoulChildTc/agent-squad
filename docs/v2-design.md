# Agent Squad v2 产品设计文档

> **项目代号：Nest**
> 一人公司 AI 团队——你当老板，它们是员工。

## 一、产品愿景

### 1.1 我们要做什么

Agent Squad v2 是一个 **AI 原生公司操作系统**，让一个人能够像管理一家公司一样管理一支 AI Agent 团队。

你只需要说"我想做什么"，AI 团队会自动完成需求分析、产品规划、技术开发、界面设计、营销推广，最终交付可运行的产品。

### 1.2 我们不做什么

- ❌ 不是又一个 Agent 框架（CrewAI、AutoGen、LangGraph）
- ❌ 不是又一个 AI 工具（ChatGPT、Claude、Cursor）
- ❌ 不是又一个代码助手（Copilot、Aider）

### 1.3 核心差异化

| 维度 | Agent Squad | 其他方案 |
|------|-------------|----------|
| 定位 | AI 原生公司操作系统 | Agent 框架 / AI 工具 |
| 关系 | 你当老板，它们是员工 | 你用它 |
| 交互 | 说人话 | 写代码 / 配 YAML |
| 角色 | 5 个公司角色（COO/CPO/CTO/CMO/CDO） | 通用 Agent |
| 场景 | 一人公司做产品 | 写代码 / 通用任务 |

### 1.4 一句话价值主张

> **别人用 AI 写代码，你用 AI 开公司。**

## 二、用户画像

### 2.1 目标用户

**主要用户**：独立开发者、自由职业者、一人公司创始人

**用户特征**：
- 技术能力：会写代码，但不是全栈专家
- 产品能力：有想法，但不懂产品规划和营销
- 时间精力：一个人干所有活，时间严重不足
- 预算限制：请不起员工，但愿意为 AI 工具付费
- 工作方式：习惯用 CLI 工具，喜欢本地优先

### 2.2 典型场景

**场景 1：从零开始做一个 SaaS 产品**
- 用户说："我想做一个帮助自由职业者管理客户和项目的 SaaS 工具"
- AI 团队交付：Landing Page + PRD + 技术架构 + 营销策略 + 开发计划

**场景 2：快速验证一个产品想法**
- 用户说："我想验证一下这个想法有没有人愿意付费"
- AI 团队交付：Landing Page + 用户访谈问题 + 定价策略 + 获客渠道

**场景 3：迭代现有产品**
- 用户说："我的产品转化率太低，帮我优化一下"
- AI 团队交付：转化漏斗分析 + 落地页优化方案 + A/B 测试计划

### 2.3 核心痛点

| 痛点 | 现状 | Agent Squad 解决方案 |
|------|------|---------------------|
| 不知道做什么功能 | 凭感觉做功能，经常做错 | CPO 角色自动输出 PRD、用户流程、MVP 规划 |
| 不懂营销 | 做了产品没人知道 | CMO 角色输出获客策略、落地页文案、转化优化 |
| 不懂设计 | 界面丑、体验差 | CDO 角色输出 UI 设计、视觉规范、落地页设计 |
| 协调成本高 | 多个 AI 工具来回切换 | COO 角色自动调度、整合结果、管理进度 |
| 文档混乱 | 代码和文档分散，找不到 | 统一文档管理，按项目/类型自动归档 |
| 没有记忆 | 每次重新开始，不记得之前的决策 | 共享记忆系统，自动积累知识 |

### 4.3 多实例架构

**核心思路**：每个 Agent 运行在独立的 OpenCode 实例中，通过文件系统共享记忆。

**为什么不用单实例的 task 工具？**
- task 工具是串行阻塞的，无法真正并行
- 子 Agent 每次都是全新会话，上下文丢失
- 无法实现 Agent 之间的直接协作

**多实例的优势**：
- 真正的并行执行
- 每个 Agent 有独立的会话和上下文
- 通过文件系统实现共享记忆
- 天然支持分布式部署

### 4.4 记忆系统

**两层记忆架构**：

```
.agent/
├── memory/                    # 私有记忆（每个 Agent 独立）
│   ├── coo.md                 # COO 的工作记录、决策偏好
│   ├── cpo.md                 # CPO 的产品分析、用户洞察
│   ├── cto.md                 # CTO 的技术决策、架构笔记
│   ├── cmo.md                 # CMO 的营销策略、渠道分析
│   └── cdo.md                 # CDO 的设计规范、视觉偏好
│
├── shared/                    # 公共记忆（所有 Agent 共享）
│   ├── CONTEXT.md             # 项目全局状态
│   ├── DECISIONS.md           # 历史决策记录
│   ├── TASKS.md               # 任务状态
│   └── KNOWLEDGE.md           # 项目知识库
│
└── queue/                     # 任务队列
    ├── pending/               # 待执行
    ├── active/                # 执行中
    ├── completed/             # 已完成
    └── failed/                # 失败
```

### 4.5 上下文注入机制

**通过 SDK 启动 OpenCode 实例时，注入记忆路径提示词**：

```
你是 CTO（技术助手）。

## 记忆系统

你有两层记忆：

1. **私有记忆**：`.agent/memory/cto.md`
   - 这是你的工作记录、技术决策、学习笔记
   - 每次任务开始前读取，任务完成后更新

2. **公共记忆**：
   - `.agent/shared/CONTEXT.md` — 项目全局状态
   - `.agent/shared/DECISIONS.md` — 历史决策记录
   - `.agent/shared/TASKS.md` — 任务状态

## 工作流程

1. 任务开始前：读取私有记忆和公共记忆
2. 执行任务：基于上下文做出决策
3. 任务完成后：更新私有记忆，如有重要决策更新公共记忆
```

## 五、角色设计

### 5.1 角色架构

```
用户（老板）
    ↓ 任何想法/需求
协调者（COO）← 总调度
    ├── 产品顾问（CPO）← 需求分析、产品规划
    ├── 技术助手（CTO）← 技术选型、代码开发
    ├── 增长顾问（CMO）← 获客策略、营销文案
    └── 设计顾问（CDO）← UI 设计、品牌视觉
```

### 5.2 协调者（COO）

**定位**：团队的总协调者，负责任务分配、进度控制和结果整合

**核心职责**：
1. 理解用户需求，判断任务类型
2. 分配任务给合适的 Agent
3. 跟踪任务进度，确保按时交付
4. 审核子 Agent 的输出，确保质量
5. 协调多个子 Agent 的协作，解决冲突
6. 维护公共记忆（CONTEXT.md、DECISIONS.md）

**决策边界**：
- ✅ 自主决策：任务分配、输出质量判断、返工决策、整合方式
- ❌ 需询问用户：重大方向变更、资源限制、用户偏好

### 5.3 产品顾问（CPO）

**定位**：专注于小型软件产品的产品经理

**核心职责**：
1. 需求分析：分析用户需求，提炼核心痛点
2. 产品规划：设计产品功能架构和用户流程
3. 功能设计：输出 PRD 和功能需求文档
4. 竞品分析：分析竞品，找到差异化机会
5. 开发计划：制定开发计划和里程碑

**输出格式**：
- PRD（产品需求文档）
- 用户流程图
- 功能优先级矩阵
- 开发计划

**核心原则**：
1. 只做 MVP，永远先做能验证核心价值的最小功能集
2. 所有功能都必须能直接或间接带来收入
3. 用最简单的方式实现需求

### 5.4 技术助手（CTO）

**定位**：经验丰富的全栈开发工程师

**核心职责**：
1. 技术选型：根据产品需求进行技术选型和架构设计
2. 代码开发：编写前后端代码和数据库脚本
3. 测试部署：进行单元测试、集成测试、部署产品
4. 问题解决：解决运行过程中出现的技术问题

**输出格式**：
- 技术架构文档
- 可运行的代码
- 部署文档
- API 文档

**核心原则**：
1. 优先使用成熟的技术栈和现成的解决方案
2. 代码只要能稳定运行即可，不追求过度设计
3. 确保产品安全、稳定、易于维护

### 5.5 增长顾问（CMO）

**定位**：专门服务独立开发者的营销销售专家

**核心职责**：
1. 获客策略：制定产品的整体营销推广计划
2. 渠道推荐：推荐最适合的获客渠道
3. 文案写作：生成高转化的推广文案
4. 转化优化：设计产品落地页的内容结构和转化逻辑

**输出格式**：
- 营销策略文档
- 获客渠道清单
- 推广文案
- 落地页内容

**核心原则**：
1. 永远只深耕一个最适合的渠道，不分散精力
2. 所有内容都围绕"解决痛点 + 展示价值 + 引导购买"展开
3. 拒绝任何需要大额广告预算的获客方式

### 5.6 设计顾问（CDO）

**定位**：专注于 B 端和工具类产品的 UI/UX 设计师

**核心职责**：
1. 视觉设计：设计产品的整体视觉风格和色彩方案
2. 界面设计：绘制所有页面的 UI 设计稿
3. 品牌设计：设计产品的 logo、图标等视觉元素
4. 落地页设计：设计高转化率的产品落地页

**输出格式**：
- UI 设计稿
- 设计规范
- 落地页 HTML

**核心原则**：
1. 功能优先，美观其次
2. 遵循主流的设计规范，减少用户学习成本
3. 使用现成的设计系统和组件库

### 5.7 写作风格约束（待研究）

**核心原则**：文档是给 AI 读的，不是给人读的。

**风格要求**：
- 结构化：清晰的标题、列表、表格，方便解析
- 简洁：无废话、无修辞、无过渡句
- 省 token：用最少的文字表达最多的信息
- 机器友好：优先使用结构化格式（如 JSON、YAML、表格）

**待研究**：具体的格式规范（如是否统一用某种模板、是否用特定的标记语言等）。

### 5.8 角色权限与工具配置（待研究）

**需求**：每个不同的角色，应该支持绑定或内置一些 Skill、MCP、或其他工具。

**待确认**：OpenCode 是否支持对每个 Agent 做细粒度的权限配置（控制 Skill、MCP、工具的访问权限）。需要后续详细研究。

## 六、协作机制

### 6.1 任务分配机制

**COO 收到用户需求后的处理流程**：

```
用户输入
    ↓
COO 分析任务类型
    ↓
判断：单一角色可完成？
    ├─ 是 → 直接分配给对应角色
    └─ 否 → 拆分子任务，分配给多个角色
         ↓
         判断：需要讨论？
              ├─ 是 → 并行调用多个 Agent，收集意见
              └─ 否 → 并行执行，各自完成
```

**任务类型 → 角色映射**：

| 任务类型 | 分配给 |
|----------|--------|
| 产品需求、功能设计、用户痛点分析 | CPO |
| 技术选型、代码开发、bug 修复 | CTO |
| 界面设计、交互设计、落地页设计 | CDO |
| 营销推广、获客渠道、文案写作 | CMO |
| 决策建议、技术选型建议 | COO + 相关角色 |

### 6.2 Agent 间通信机制

**通信方式**：通过文件系统，Agent 之间不直接通信

**通信流程**：
1. COO 分配任务，写入任务队列
2. Agent 从队列读取任务
3. Agent 执行任务，更新私有记忆
4. Agent 将结果写入指定位置
5. COO 读取结果，整合后返回给用户

### 6.3 冲突解决机制

**冲突类型**：
1. 技术方案冲突：CTO 和 CDO 对实现方式有分歧
2. 产品方向冲突：CPO 和 CMO 对目标用户有分歧
3. 优先级冲突：多个任务同时需要资源

**解决流程**：
```
冲突发生
    ↓
COO 识别冲突类型
    ↓
COO 召集「冲突裁决会」
    ↓
并行调用相关 Agent，收集意见
    ↓
COO 做出最终裁决（或上报用户）
    ↓
更新 DECISIONS.md，记录裁决结果
```

**裁决原则**：
1. 用户价值优先（用户体验 > 技术实现）
2. MVP 原则（能验证核心价值的最小功能集）
3. 收入优先（能直接或间接带来收入的功能）

### 6.4 会议机制

**会议类型**：
- **项目启动会**：新项目开始时，所有角色对齐目标
- **需求评审会**：CPO 输出 PRD 后，CTO 和 CDO 评审可行性
- **技术选型会**：需要技术决策时，CTO + COO 讨论
- **冲突裁决会**：Agent 之间有分歧时，COO 协调裁决

**会议流程**：
1. COO 确定会议类型和参会人员
2. 并行调用参会 Agent，收集意见
3. COO 综合各方意见，做出决策
4. 生成会议纪要，存入 `docs/会议纪要/`

```
└── DECISIONS.md
```

**命名规范**：

| 文档类型 | 命名格式 | 示例 |
|----------|----------|------|
| 需求文档 | `PRD-名称.md` | `PRD-MVP需求文档.md` |
| 技术文档 | `技术-名称.md` | `技术-架构设计.md` |
| 设计文档 | `设计-名称.md` | `设计-UI规范.md` |
| 营销文档 | `营销-名称.md` | `营销-获客策略.md` |
| 会议纪要 | `YYYY-MM-DD-主题.md` | `2026-06-08-项目启动会.md` |
| 进度文档 | `进度-YYYY-MM.md` | `进度-2026-06.md` |
| 规范文档 | `规范-名称.md` | `规范-多Agent协作.md` |

**文档元数据（frontmatter）**：

```markdown
---
title: 文档标题
project: 项目名称
type: 需求文档 / 技术文档 / 设计文档 / 营销文档 / 会议纪要
author: cpo / cto / cdo / cmo / coo
created: 2026-06-08
updated: 2026-06-08
status: draft / review / approved
tags: [MVP, SaaS, 自由职业者]
---
```

**Agent 读写规则**：
- 产出的文档必须存放到对应目录
- 命名规范自动执行
- 每次任务完成后 Git commit
- commit 格式：`docs: 添加 PRD-新功能` 或 `docs: 更新 技术-架构设计`

**文档检索**：
- 按目录检索：知道文档类型，直接去对应目录找
- 按命名检索：知道文档名称，用 `find` 或 `ls` 找
- 按内容检索：知道关键词，用 `grep` 搜索
- 按时间检索：知道创建时间，用 `ls -lt` 排序

## 十二、风险与挑战

### 12.1 技术风险

| 风险 | 严重程度 | 应对方案 |
|------|----------|----------|
| OpenCode SDK 不稳定 | 中 | 关注 OpenCode 更新，必要时降级 |

| 文件系统并发冲突 | 低 | 使用文件锁，避免同时写入 |

| 风险 | 严重程度 | 应对方案 |

| 功能过多导致复杂 | 中 | MVP 聚焦核心功能，渐进式扩展 |
| 竞品模仿 | 低 | 保持轻量级和本地优先的差异化 |

### 15.1 关于记忆生效的优化

**核心思路**：通过 SDK 启动 OpenCode 实例时，注入记忆路径提示词，让每个 Agent 自动知道去哪找记忆。

**注入的提示词模板**：


### 15.2 关于 OpenCode 的选择

**OpenDesign** 是一个开源的设计工具（[manalkaff/opendesign](https://github.com/manalkaff/opendesign)），定位是 "claude.ai/design open-sourced!"——类似 Claude 的设计能力，但完全开源。

**集成方式**：
- CDO（设计顾问）生成的设计稿可以直接通过 OpenDesign 渲染
- 用户可以在 Web UI 中直接看到可交互的设计原型
- 支持实时预览、修改、导出

**集成价值**：
- CDO 的输出从"设计文档"升级为"可交互的设计稿"
- 用户不需要额外的设计工具，一站式完成
- 设计 → 开发的流程更顺畅

**实现阶段**：Phase 4（9-12 周）

**技术方案**：
- 通过 OpenDesign 的 API 或 MCP 集成
- CDO 生成设计规范 → OpenDesign 渲染为可交互原型
- Web UI 中嵌入 OpenDesign 的预览组件

### 15.3 关于 OpenCode 的选择

**选择 OpenCode 作为运行时的原因**：
1. 开源（160K stars，7.5M 月活）
2. 功能齐全（75+ LLM、MCP、Skills、上下文压缩）
3. 社区活跃（持续更新）
4. 有 SDK（支持编程控制）
5. 不需要自己实现 Agent 基础功能

**不选择其他方案的原因**：
- Pi：需要自己建太多东西（8-13 周）
- Goose：功能不如 OpenCode 丰富
- OpenHands SDK：Python 生态，迁移成本高
- 自建运行时：重复造轮子

### 15.4 关于 dogfooding（用 v1 开发 v2）

**想法**：用 Agent Squad v1 来开发 Agent Squad v2。

**现状**：v1 是不可用的 demo，但仍然可以用于一些具体、独立的任务：
- 写代码：Developer Agent 能写独立模块
- 调研分析：Advisor Agent 能搜索和分析
- 写文档：需要手动注入大量上下文

**价值**：
- 在使用 v1 的过程中，会更清楚它的痛点
- 这些痛点就是 v2 要解决的问题
- 真正的 dogfooding

### 15.5 关于 A2A 协议

**现状**：A2A（Agent-to-Agent Protocol）是 Google 提出的 Agent 间通信协议，目前还在早期阶段。

**跟我们的关系**：
- 短期（MVP）：不需要，用 OpenCode 的 task 工具和文件系统就够了
- 长期（平台化）：可能需要，如果做 Agent 市场，让用户能雇佣不同框架的 Agent，A2A 就有价值了

**参考**：https://github.com/a2aproject/A2A

### 15.6 关于 agentgateway

**是什么**：Agent 世界的 Nginx——统一网关，管理 Agent 间通信、MCP、LLM 调用。

**跟我们的关系**：可以参考它的架构设计，但我们不需要自己实现。OpenCode 已经处理了 Agent 执行和工具调用。

**参考**：https://agentgateway.dev

### 15.7 关于 Goose 对比

**Goose** 是另一个开源 AI Agent（47.9K stars），由 Block（Square）开发，现在归 AAIF（Linux Foundation）。

**跟 OpenCode 的对比**：

| 维度 | OpenCode | Goose |
|------|----------|-------|
| Stars | 160K | 47.9K |
| 语言 | Go | Rust |
| 形态 | 桌面+终端+IDE | 桌面+CLI+API |
| LLM | 75+ | 15+ |
| 社区 | 更大 | 较小 |

**结论**：OpenCode 更强大，社区更大。选择 OpenCode 是正确的。

### 15.8 关于 Hashline 编辑（待研究）

**来源**：Oh My Open Agents (OmO) 的核心功能。

**是什么**：每行代码带哈希锚定，让 Agent 精确定位代码位置。

```
11#VK| function hello() {
22#XJ|   return "world";
33#MB| }
```

**效果**：编辑成功率从 6.7% 提升到 68.3%。

**集成方式（两种思路）**：
1. **做成 OpenCode 插件**：开发一个 OpenCode 插件，实现 Hashline 编辑功能
2. **安装时自动安装插件**：Agent Squad 安装时，自动帮用户把 Hashline 插件安装到 OpenCode 中

**待研究**：
- 分析 OmO 的 Hashline 源码实现
- 确认 OpenCode 是否支持这种插件
- 评估实现难度

### 15.9 关于 Token 管理（待研究）

**需求**：追踪每个 Agent 的 Token 使用情况，用于成本核算和优化。

**需要追踪的指标**：
- **输入 Token**：每次请求发送的 Token 数量
- **输出 Token**：每次响应返回的 Token 数量
- **缓存命中率**：缓存命中的 Token 占总 Token 的比例（缓存 Token 通常更便宜）

**技术挑战**：
- 不同模型有不同的分词器（GPT 用 tiktoken，Claude 用自己的，国产模型各有各的）
- 需要针对每个模型计算准确的 Token 数量
- OpenCode 是否暴露了 Token 使用数据？需要调研

**实现思路**：
1. 通过 OpenCode SDK 获取 Token 使用数据
2. 针对不同模型使用对应的分词器计算
3. 记录到每个 Agent 的私有记忆中
4. 汇总到项目的成本核算模块

**待研究**：
- OpenCode SDK 是否提供 Token 使用数据
- 各模型分词器的 Node.js 实现
- 缓存命中率的获取方式

### 15.10 关于竞品功能补充（待研究）
